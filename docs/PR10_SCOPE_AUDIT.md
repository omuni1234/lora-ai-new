# PR #10の範囲監査と観測ログの境界

2026-10-22に、PR #10のマージ前 `6111632`、PR head `e9a74b1`、マージ後main `5f0e45d` を比較した記録です。対象は「Experiment YAML・分析の追加・既存変数のログ取得」が、既存シミュレーションの計算を変更していないかという確認です。

## 複合損失の導入時期と意味

`MixedLoss` はPR #10より前から存在します。`engine.py`の導入コミットは `d757722`、共通分析側は `aab05c5`。PR #10前の `6111632` と現在の `_uplink_result` は、次の判定規則が同じです。

1. 1 GW以上で受信できれば `Received`。
2. 成功がなく、必要な受信判定が未了なら `Censored`。
3. 全GWで同じ理由により失敗した場合、その理由。
4. 全GWで失敗し、理由が異なる場合 `MixedLoss`。

例として、GW0で `LostBecauseTx`、GW1で `UnderSensitivity` なら、1個のULのネットワーク分類は `MixedLoss` です。新しい物理的な損失要因を生成したものではありません。PR #10のTVT YAMLは4 GW構成のため、この既存分類が現れ得ます。単一GWの実験と結果を比較する際には、GW数・配置も実験条件に含めてください。

この分類を干渉・感度未満などへ恣意的に再配分すると、分母や原因の意味が変わります。保存済みのGW別判定をそのまま表示する `gateway_outcomes` を追加しました。[使い方・分母](ANALYSIS.md#gw別の受信結果と複合損失の内訳)を参照してください。既存のネットワークPRR・損失の集計式は同じです。

## ログ取得が守る境界

- 無線イベントの時刻・順序・受信判定・乱数抽選を変えない。
- `motion_epoch_start()` は既存の `position(t)` の後で呼ばれ、移動を進めず乱数も消費しない。
- 時刻指定・順路モードなどで保持していない状態開始時刻はnull。送信位置から推測して埋めない。
- 診断情報を選択器の `Observation` / `Feedback` に追加しない。
- `process_time_ns()`の測定値をsimulation timeや報酬に戻さない。
- ホスト計測の実行時間は揺らぐ。特にMCUの `measured` モードはコールバックのwall timeに内部診断の負荷も含むため、消費エネルギーの完全一致は保証しない。固定時間モードのエネルギーは回帰テスト対象。
