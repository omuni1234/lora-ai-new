# ハイパーパラメータ調整（v0.13）

「モデルライブラリ」から、モデルの定数を小さな予算で比較し、新しい再利用定義として保存します。探索はworkerが管理します。ブラウザー・SSHセッションの切断は探索を止めません。物理層・MAC・EDごとの独立学習の実装は通常のRunと共通です。

## 操作

1. 実験ワークスペースで、ED数、位置・移動、送信間隔、行動空間などの比較条件を設定します。YAMLを編集中なら先にGUIへ反映します。
2. モデルライブラリのカードで「このモデルを調整」を押します。保存済み定義も対象です。あるいは定義エディタで変更後、「編集モデルと現在の実験条件を取り込む」を押します。
3. モデルを適用するEDグループを選びます。選択グループの当該カテゴリを取り込んだ定義で置換します。他カテゴリ・対象外グループは維持します。C0は**選択モデルの変更前の定数**であり、変更前プロファイルの別アルゴリズムではありません。
4. 調整する項目を追加し、候補値を指定します。例：`epsilon` に `[0.02,0.1,0.3]`、`learning_rate` に `[0.0001,0.001,0.01]`。数値範囲から線形・対数間隔の候補を生成でき、整数にも丸められます。
5. 探索方法、評価時間、探索用seed、独立した確認用seedを設定し、「評価予算を確認」を押します。必要なら公平性・損失・エネルギーの重みを指定します。
6. 「バックグラウンドで調整開始」を押します。既存のworkerが通常Runと同じ並列枠で評価します。worker未起動なら登録状態のまま待機します。
7. 評価時間ごとの表・PRRグラフと、別seedでの確認結果を見ます。各表はCSV、探索全体はJSONで保存できます。元のRunは専用Experimentに残り、「比較・分析」から詳しく調べられます。
8. 候補と新しい名前を指定してライブラリへ保存します。その後、EDグループのモデル参照から利用できます。同名は上書きしません。

保存されるのは `kind`、`options`、`action_space` です。**学習済み重み、Q-table、経験バッファの保存ではありません。** 新しいシミュレーションではEDごとに未学習のエージェントが作られます。途中で正常評価された候補も保存できますが、最終確認済みとは限りません。保存履歴には探索ID・候補ID・カテゴリ・保存名を記録します。

## 探索方法

| 方法 | 評価の配分 | 用途・制約 |
|---|---|---|
| 段階的な絞り込み | 有限候補の直積から重複なく抽出し、短時間→中時間→長時間。各段階の上位約1/reductionを残す | 大きい候補空間の一次選別。学習が遅い候補を早期に落とす可能性あり |
| 逐次局所探索 | 最短時間で1座標の隣接値を探索。悪化も確率的に受理。ランダム再探索あり。上位候補を最長時間で再評価 | 高次元・非単調な目的関数。数値の候補は昇順に登録する |
| 網羅探索 | 指定した直積の全候補を**最長時間**・同じseed集合で評価 | 小さい空間の確実な比較。短時間で打ち切る候補選別は行わない |

1探索は最大12項目・各項目64値・探索候補上限128、探索/確認seedはそれぞれ最大8個です。元定義C0は別枠で各比較段階に残します。各段階は時刻0から再実行し、学習状態を引き継ぎません。短い実験の終了処理済み状態を長い実験へ継ぎ足すと因果関係を変えてしまうためです。同じ探索内で候補・時間・seed集合が一致する正常評価は再利用します。他の探索や異なるバージョンの結果は使い回しません。

局所探索で最大化するスコア差を Δ、新規候補番号に対応するステップを k とすると、悪化の受理確率は `exp(Δ / T_k)`、温度は `max(1e-12, temperature * cooling^(k-1))` です。改善・同点は受理します。隣接関係は候補リストの順序で決まり、一定確率で未評価の別領域へ移ります。既評価候補の再訪を省く、有限予算の焼きなまし型ヒューリスティックです。古典的な焼きなまし法の収束保証や、鞍点・局所解からの脱出保証を主張しません。

段階的な予算配分は [Li et al., Hyperband, JMLR 2018](https://www.jmlr.org/papers/v18/16-558.html) に記載されるSuccessive Halvingの考え方を使っています。本実装は単一の評価時間系列で選別し、Hyperbandの複数bracket全体やASHAを再現したものではありません。対象モデルの学習と、外側の探索処理は別です。

## 評価時間の決め方

ED数を減らすと干渉・GW送信中損失・チャネル競合が変わるため、本機能はED数を縮小しません。PHY/MACも置き換えません。省くのは多数の候補に対する長時間評価です。選択アルゴリズムの性能は学習に依存するので、Calculatorの確率近似だけで順位を決めることもしません。

GUI初期値の最長時間は `min(元実験時間, 36000秒)`、基本の段階比は1/9、1/3、1です。既知のperiodic/poissonの間隔と、選択モデルの `batch_size` / `history_range` を使い、初段をある程度延ばす補助があります。数値は編集できます。候補にさらに大きなbatch_size等を追加した場合、予算確認で不足を警告します。この補助はアプリケーション生成数の目安で、MAC待機、Duty cycle、再送、学習プラグイン固有の条件、移動周期を正確に予測しません。

最低限、ランダムな送信開始の範囲、学習のウォームアップ、調べたい静止・移動の双方を含む長さにします。DQNで32経験から学習するなら、数回送信だけの評価で候補を選別するのは不適切です。早期のPRR最大化と長期収束後のPRR最大化は別の目的なので、長期性能が主目的なら初段も十分長くしてください。

「評価予算を確認」は元実験何回分の**仮想時間**を使うかの上限です。実時間の予測・高速化倍率ではありません。実際のCPU時間はED数、衝突状態、選択器、記録量、並列数に依存します。段階ごとの再実行、C0、確認seedを含むため、小さな候補集合では絞り込みの方が安くなるとは限りません。最長時間が元実験より短ければ、保存後に元の時間でも確認してください。

## スコアの定義

既定は全ED平均UL PRRの最大化です。各Runについて、判定済みULのあるEDのPRR平均に、そのED数 / 全ED数を掛けます。つまり未送信EDをPRR 0として含めます。通常の分析画面で表示する「対象EDだけの平均」と分母が違う場合があるので、ED観測割合も表示します。短い実験で送信した少数EDだけを有利に評価しないためです。

任意の重みを加えると、最大化する値は次です。

```
score = PRR_all
      - w_interference * interference_all
      - w_gateway_tx  * gateway_tx_all
      - w_sensitivity * sensitivity_all
      + w_fairness    * Jain_all
      - w_energy      * joules_per_received_uplink
```

損失割合も全ED等重みで、未送信EDの当該損失は0です。Jain indexは未送信EDをPRR 0として含め、全EDが成功0の場合は探索用スコアでは0にします。損失の減点はPRRに反映済みの損失を追加で重視する項目です。総和1の確率分布を新たに作る式ではありません。

エネルギーはRun全期間の無線総エネルギーと、選択時にはMCU総エネルギーを足し、成功UL数で割ったJです。待機・起動時を含む総量なので、送信回数区間を指定した分析画面のエネルギーとは範囲が異なります。無線モデルが無効ならN/A。エネルギー重みを使う際には無線モデルを必須とし、成功ULが0件の候補は評価不能にします。MCUの実時間計測を使うとCPU負荷・並列実行数に影響されます。

seedごとにスコアを計算して平均し、seed間の標本標準偏差も表示します。1 seedでは標準偏差はN/Aです。エラーバーはseed間の最小〜最大で、信頼区間ではありません。最適化対象は対象外グループも含めたネットワーク全体です。

既定では、判定済みULがあるED割合90%以上、全EDあたり平均判定済みUL数1以上を要求します。これは**各EDが最低1回送信した保証ではありません**。下限は調整可能です。終端で判定未了となるULは成功・損失の分母から除外し、件数を別表示します。終了境界の影響が大きい場合は時間を延長してください。探索に含まれるいずれかのseedで失敗・観測不足なら、その候補の当該段階全体を無効にし、成功seedだけの平均で昇格させません。

## 独立seedでの確認

最長時間の探索結果から勝者を固定し、その候補とC0を別のseed集合で再実行します。確認結果から候補の選び直しはしません。改善しなかった場合も値をそのまま表示します。少数seedでの差は統計的な改善保証ではありません。確認用seedを見ながら何度も探索し直すと、そのseedにも過適合するので、研究の最終比較にはさらに未使用のseedを用意してください。

同じseedを全候補で共有しますが、実装ごとの乱数消費やイベント順により、すべての乱数イベントが1対1に対応するとは限りません。重みや環境を変えた探索同士のスコアを直接順位付けしないでください。

## 開発者向け

選択器、移動、送信タイミングの3カテゴリに対応します。標準の `Options`（Pydantic）から型・既定値・範囲・日本語title/description・enumを読みます。独自プラグインも同じインターフェースです。数値、bool、enumの候補を提示しますが、推奨値の保証はありません。

入れ子は `start.max_s`、配列要素は `hidden_sizes.0` のように手動登録できます。親オブジェクトや配列は先にモデル定義で設定してください。探索値はJSON配列なので、文字列や配列全体の候補も指定できます。実行時には各組み合わせをOptionsとプロファイルで検証し、相互制約に違反する候補は理由付きで記録します。共通行動空間によって上書きされる無線設定は候補提示から除外し、手動指定も拒否します。学習ハイパーパラメータと行動空間の条件を混同しません。

条件による割り当てが対象グループのモデルを上書きする場合は開始を拒否します。該当する割り当てを外すか、明示的なグループ設定に整理してください。移動・送信タイミングそのものを調整する場合は研究環境も変わるため、同条件の選択アルゴリズム比較とは区別します。

- `lorasim/tuning.py`: 設定、候補提示、探索制御、指標、保存、API。
- `lorasim/jobs.py`: 永続テーブルと既存workerからの進行処理。
- `lorasim/static/tuning.js`: フォーム、予算・結果表示、ライブラリ登録。
- `tests/test_tuning.py`: 探索・独立確認・中止・再接続・保存・実workerの検証。
- `examples/tuning_bandit.py`: 小さい探索を登録するPython例。

APIは `POST /api/tuning/suggestions`、`POST /api/tuning/preview`、`POST /api/tuning`、`GET /api/tuning`、`GET /api/tuning/{id}`、`POST /api/tuning/{id}/cancel`、`POST /api/tuning/{id}/save`。通常のAPI認証設定を共用します。プレビュー・候補提示はシミュレーションを起動しません。

探索設定・全プロファイル・候補・段階別のRun ID・seed・指標・選択結果はSQLiteに保存し、GUIでJSONを取得できます。各RunのParquet/profile/manifestは通常通り残ります。1探索は独立したExperiment（名前に`[調整]`）です。通知Webhookは評価Runでは無効化します。大量の試行ごとの通知を避けるためです。

ジョブ投入と探索状態の更新は1トランザクションです。worker再起動時にも同じ段階を重複投入しません。プロセス異常終了のRunは通常worker同様に失敗・中断として扱い、シミュレーション途中の状態から復元はしません。探索を中止すると、当該探索の待機Runを取消し、実行中Runへ停止を要求します。他の実験は変更しません。探索作成時とworkerのリリースが違う場合は継続を拒否します。

記録は既存の分割Parquetで流し書きし、指標は終了時に生成したアブストラクトから取得します。探索のポーリングはパケット全件を再集計しません。独自モデルのコード配置・有効化はAPIとworkerの両方に必要です。
