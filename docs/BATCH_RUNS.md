# ED数 × 選択アルゴリズムの一括実行

実験ワークスペース上部の **「ED数 × アルゴリズム · 一括実行」** で、候補リストの直積をキューへ登録します。通常のRunと同じworker・並列枠・進捗・キャンセル・結果・分析を使います。PHY/MACやイベント処理方式は変更しません。

## 操作

1. 元のプロファイルでエリア、GW、送信間隔、移動、共通行動空間、時間、seedを設定します。YAML編集中ならGUIへ反映します。
2. 一括実行を開き、総ED数に `100, 200, 300` と入力します。カンマ、読点、空白、改行で区切れます。
3. 選択アルゴリズムを選び「リストに追加」。内蔵 `bandit` と `dqn` なら3×2で6 Runです。現在のグループ設定、保存済みモデルライブラリ、プロファイル内の定義も選べます。
4. 必要なら比較名と保存先Experimentを変更します。定数・行動空間は各行の詳細で確認できます。調整済みの値を使う場合はその保存定義を選びます。内蔵を選んだ場合は初期値です。
5. 「組み合わせを確認」で全候補のモデル初期化まで検証し、配分・Experiment・Warningを表で確認します。この段階ではRunは作成されません。
6. 「確認したRunをキューに追加」で登録します。画面を閉じてもworkerは実行を続けます。

画面を開いた時点のプロファイルとモデル定義を固定します。元設定を変えた場合は、一括実行画面を開き直してください。候補を編集すると確認結果を無効化します。

## Experimentとの対応

標準では**アルゴリズムごとに1つの新規Experiment**を作成し、その中にED数の異なるRunをまとめます。100・200・300台×Bandit・DQNでは、2つのExperimentに3 Runずつ入ります。「比較・分析」でこの2つをチェックして分析します。

既存分析がExperimentとED数を単位としてRunを集計するため、この構成にしています。各行で既存Experimentも選択できますが、複数のアルゴリズムに同じ保存先は指定できません。既存Runの選択器や条件との一致は利用者が確認してください。通常実行のExperiment選択は一括実行へ継承しません。単一Run・既存Experiment・seed sweepは従来どおりです。

## 展開ルール

- ED数は全グループの合計。複数グループは元の比率で整数配分します。各グループ最低1台、端数は最大剰余順、同値なら元のグループ順です。最低台数制約による比率のずれもあるため、確認表で配分を確認してください。
- 選択器を全グループへ適用します。`assignments` の選択器上書きも置換し、別選択器が残るのを防ぎます。移動・送信タイミングの割り当ては維持します。
- 行動空間と定数は選択モデルの定義に従います。内蔵モデルは通常GUIでそのモデルを選んだときと同じ初期値・共通空間設定です。候補集合を自動で揃え直すことはしません。
- 送信、移動、位置観測、Confirmed、PHY/MAC、時間、seed、エネルギー、通知は元のままです。SEMAの位置観測が未許可、DQNがUnconfirmedなどの場合は自動変更せずエラーにします。
- ED数変更に伴い配置・連番ID・乱数ストリームの対応が変わる場合があります。異なるED数間で同じEDの座標や履歴が一致する保証はありません。
- 台数が変わるグループが明示座標（`explicit`）を使う場合、またはED ID条件の割り当てがある場合は登録を止めます。座標の複製・切り詰めや、ID対象の推測変更は行いません。
- ED数の重複は不可。ED数候補は最大50、選択器は最大20、積は最大100 Runです。並列数は右側「実行リソース」で設定します。

モデル参照は登録時の定義をRunへ埋め込みます。後からライブラリを編集しても投入済みRunは変わりません。各Run・各EDの学習状態は独立です。

## 原子的な登録と再送

全候補の検証後、ExperimentとRunを1つのSQLiteトランザクションで登録します。設定不備や途中のDB書き込み失敗で一部だけキューに入ることはありません。コミット後は通常のqueued Runとして見えます。実行時のエラーは各Runで個別に記録します。

GUIは1回の確認に対して登録IDを生成します。応答だけが切断で失われた場合、同じ画面で再送すると既存の登録結果を返し、重複Runは作りません。画面を閉じる・再確認・再読み込みすると新しい登録操作になります。結果が不明なまま新規登録する前に、実行キューを確認してください。

## API

- `POST /api/batches/preview`: `{yaml, ed_counts, policies}`。`policies` は `{name, definition, experiment_id?}` の配列。`definition` は既存Component形式で `ref` も利用可能。応答は `plan_hash`, `rows`, `run_count`, `new_experiments`, `notes`。
- `POST /api/batches`: 同じ内容に `request_id`（小文字16進32文字）と `plan_hash` を付加。応答は `jobs`, `experiment_ids`, `run_count`, `request_id`。同一ID・同一内容の再送は同じ応答、異なる内容へのID流用は409。
- 確認後に参照モデルや保存先名が変わるとハッシュが一致せず409。再確認してください。
- 両APIは既存Bearer認証に従います。

実装は `lorasim/batches.py`、画面は `lorasim/static/batches.js`。追加テーブル `batch_submissions` は再送の記録のみ。Run・Experimentとworkerが読むプロファイルのスキーマは変更していません。
